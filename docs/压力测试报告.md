# 压力测试报告

> 项目:小鱼知识库问答系统
> 测试目标:验证系统在 **100 名用户同时使用** 场景下的承载能力与稳定性
> 测试日期:2026-09-19
> 测试工具:Locust 2.46.6
> 原始数据:`report.html`(Locust 生成的完整报告)、`backend/tools/stress/results/`

---

## 一、测试结论(摘要)

系统在 100 名并发用户下**未发生崩溃,整体可用**,但暴露出**三个并发瓶颈**,导致响应时间显著变长、约 1.45% 的请求失败。

| 结论 | 说明 |
|---|---|
| ✅ 服务稳定性 | 持续压测 19 分 51 秒后服务仍正常响应,无崩溃、无内存泄漏迹象 |
| ✅ 基础性能 | 简单接口(健康检查)单场景实测 **96.5 请求/秒、中位数 3 毫秒** |
| ⚠️ 三个瓶颈 | ① 密码校验阻塞主线程 ② 数据库写锁冲突 ③ 数据库连接池耗尽 |
| ⚠️ 失败率 | 28,055 个请求中失败 407 个(1.45%),集中在需要写数据库的接口 |
| ⚠️ 响应时间 | 提问类接口中位耗时 20~24 秒,最慢达 52 秒 |

- **账号准备**:预先注册 100 个压测账号,并为每个虚拟用户分配独立账号(避免账号共享造成的额外干扰)

## 四、瓶颈根因分析

### 瓶颈① 密码校验阻塞主线程(影响:全局)

**现象:** 登录接口中位响应 **4.5 秒**(正常应低于 0.3 秒),最慢 28.7 秒;同时拖慢所有其它接口。

**原因:** 系统采用单进程异步架构,所有请求由一个"主线程"调度。而密码校验使用的 bcrypt 算法是**纯 CPU 计算,单次约耗时 100~300 毫秒,且以同步方式执行**。这意味着每次登录都会把主线程独占数百毫秒,期间**所有其它请求都无法被处理**。

**日志证据:**

- 登录场景 20 人并发即产生持续排队
- 健康检查在混合并发下从 3 毫秒劣化至 130 毫秒(该接口自身无任何耗时操作)
- 登录接口平均每秒仅完成 3.57 个请求(单独测试时该接口本可轻松达到数百)

**通俗理解:** 系统只有一位服务员,而"核对密码"这道工序必须由服务员本人站着算完。20 位顾客同时来办这道手续,服务员就被占住了,其他所有顾客(哪怕只是问一句话)都只能在门口排队。

### 瓶颈② 数据库写锁冲突(影响:所有写操作)

**现象:** 407 个失败请求中,绝大多数是**新建会话、删除会话、提问保存**这类需要写数据库的接口;提问接口失败率高达 15.5%~21.9%。

**原因:** SQLite 默认采用 rollback journal 模式,同一时刻**只允许一个写入者**,且未配置等待超时。当多个请求同时写入时,后到的会直接失败并抛出 `database is locked` 错误,而不是排队等待。

**日志证据:**

- 后端日志中 `database is locked` 共出现 **3,282 次**
- 未处理异常 506 次,分布:提问 387 次、新建会话 66 次、删除会话 36 次、登录 9 次、注册 8 次
- 提问接口的失败集中在**回答生成完毕、写入数据库**的最后一步 —— 用户已经看到回答内容,却收到错误提示,回答也未能存入历史记录

**通俗理解:** 数据库像一间只有一把钥匙的仓库,一次只能进一个人。100 个人同时要存取东西,撞门的人直接被拒之门外(报错 500),而不是排队等钥匙。

### 瓶颈③ 数据库连接池耗尽(影响:所有数据库操作)

**现象:** 部分请求等待 30 秒后超时失败。

**原因:** 数据库连接池默认上限为 **5 个常驻连接 + 10 个临时连接 = 15 个**。当瓶颈①②导致已有连接长时间被占用时,新请求排队 30 秒仍拿不到连接即报错放弃。

**日志证据:** `QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00`(出现 33 次)。

**通俗理解:** 进仓库的名额只有 15 个。前面的人卡在里面不出来,后面的人等了 30 秒还是排不上号,只能放弃。

### 三个瓶颈的连锁关系

```
密码校验阻塞主线程 ──┐
                     ├──→ 请求处理变慢 ──→ 数据库连接被长时间占用 ──→ 连接池耗尽 ──→ 更多请求超时
数据库写锁冲突 ──────┘
```

三个环节互相放大,最终表现为:所有接口一起变慢、需要写库的接口大面积报错。

## 六、改进建议(尚未实施)

> 以下建议基于本次测试数据提出,均**未实施**,后续可按需评估落地效果。

| 优先级 | 改进项 | 做法 | 预期效果 |
|---|---|---|---|
| 高 | 密码校验不再阻塞主线程 | 将 bcrypt 计算放入独立的线程池执行(`asyncio.to_thread`) | 登录不再拖慢其它请求,健康检查等接口恢复毫秒级响应 |
| 高 | 启用 SQLite WAL 模式 | 开启 WAL 日志模式并设置写锁等待超时 | 读写可并行,`database is locked` 错误大幅减少 |
| 中 | 扩大数据库连接池 | 提高连接池上限并设置合理的回收策略 | 避免请求排队 30 秒后放弃 |
| 中 | 数据库改用 PostgreSQL | 替换为支持高并发写的数据库 | 从根本上解决单写者限制(改动较大,适合后期演进) |
| 低 | 多进程部署 | 以多 worker 方式启动服务 | 需先解决限流器与缓存的多进程一致性问题 |

## 七、测试可复现说明

压测环境位于 `backend/tools/stress/`:

| 文件 | 作用 |
|---|---|
| `prepare.py` | 创建 100 个压测账号并预热问答缓存 |
| `locustfile.py` | 5 个压测场景定义 |
| `accounts.json` | 压测账号与登录令牌(测试数据,勿外传) |
| `warm_questions.json` | 用于缓存预热的 20 个问题 |
| `results/` | 各场景导出的 CSV 明细数据 |

**复现步骤:**

```bash
# 1. 以"模拟模式"启动后端(独立数据库,不调用外部 AI,不产生费用)
cd backend
set MOCK_LLM=1
set DB_FILENAME=stress.db
venv\Scripts\python.exe run.py

# 2. 准备压测数据(创建账号 + 预热缓存)
venv\Scripts\python.exe tools\stress\prepare.py

# 3. 启动压测(浏览器打开 http://localhost:8089 操作)
venv\Scripts\python.exe -m locust -f tools\stress\locustfile.py --class-picker --host=http://127.0.0.1:8000
```

**测试过程的安全保障:**

- 独立数据库,真实业务数据零接触
- AI 全部由模拟器承担,零费用、零外部依赖
- 模式开关默认关闭,不影响正常使用

## 八、总结

本次压力测试验证了系统在 100 并发用户下的真实表现:

**可用性方面**,系统在持续 20 分钟的压力下保持稳定,未出现崩溃或服务中断,基础接口性能优秀(96.5 请求/秒、3 毫秒响应),读类接口零失败。

**并发能力方面**,测试暴露出三个可定位、可复现的瓶颈:密码校验阻塞主线程、数据库写锁冲突、连接池耗尽。三者相互放大,导致写类接口失败率最高达 21.9%,提问接口中位响应时间达到 20 秒以上。

**价值方面**,本次测试将"系统能支持多少并发"从主观判断变为可量化的事实,并给出了三个瓶颈的完整证据链(日志中 `database is locked` 出现 3,282 次、连接池超时 33 次、异常分布明细),为下一阶段的性能优化提供了明确的优先级依据 —— 这正是压力测试的核心目的:**在用户遇到问题之前,先让系统在测试中暴露问题。**
